# Feature Specification: 数据管道与 Spark 挖掘

**Feature Branch**: `001-data-pipeline-spark-mining`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "数据管道与 Spark 挖掘功能。从 Stack Exchange（主源）和 arXiv CS（补充源）采集原始数据，统一为文档结构；Spark 批处理完成文本清洗、去重、TF-IDF 关键词抽取、KMeans 主题聚类、文档间相似度计算；输出写入 MongoDB 的 documents 和 mining_results 两个集合；第一技术切片两源各 100 条打通全链路，再扩展到不少于 10,000 条有效 Stack Exchange 文档及 arXiv 补充数据；每条结果带 batch_id，保留 Spark 日志和 DAG 作为课程证据。"

### User Story 1 - 打通最小链路验证（Priority: P1）

下游开发者（负责个性化分类与 Web API 的团队成员）需要先用小规模数据确认整条链路
（采集 → 统一字段 → Spark 处理 → 写入存储）真的跑得通，再决定是否放大到全量数据。

**Why this priority**: 这是后续所有工作的前提。如果最小链路跑不通，扩大规模只会放大
返工成本；课程答辩也要求先有可运行证据，再有规模证据。

**Independent Test**: 分别从两个来源各提供 100 条原始文档作为输入，触发一次处理流程，
不依赖任何下游功能，仅检查存储中出现的文档与挖掘结果记录即可判定成功。

**Acceptance Scenarios**:

1. **Given** 两个来源各 100 条原始文档，**When** 触发一次处理流程，**Then** 存储中出现
   200 条统一字段的文档记录，且每条记录的必填字段（来源、标题、正文、时间、原文链接）
   均非空。
2. **Given** 上一步已完成的 200 条文档，**When** 处理流程执行完毕，**Then** 每条文档
   对应一条挖掘结果记录，包含非空的关键词列表、一个主题簇归属，并标注本次处理的批次
   标识。

---

### User Story 2 - 规模化处理与课程证据留存（Priority: P2）

课程评审者/教师需要看到本功能在真实规模（不少于 10,000 条有效数据）下运行的证据，
以确认"大数据处理"不是摆样子的技术名词。

**Why this priority**: 课程评分明确要求规模证据，但只有在最小链路（P1）验证通过后
再放大规模才有意义，所以排在第二优先级。

**Independent Test**: 提供不少于 10,000 条来自两个来源的原始文档，触发处理流程，检查
最终产出的文档与挖掘结果数量、处理耗时记录、任务执行日志是否存在且可读。

**Acceptance Scenarios**:

1. **Given** 不少于 10,000 条有效原始文档，**When** 处理流程执行完毕，**Then** 存储中
   产出的文档记录数与去重后的有效输入数一致，且每条记录都能关联到本次运行的批次标识。
2. **Given** 一次已完成的规模化处理运行，**When** 查看该次运行的执行记录，**Then** 可以
   看到处理起止时间、输入条数、产出条数、失败/跳过条数，作为可核查的运行证据。

---

### User Story 3 - 重复运行与数据更新（Priority: P3）

数据源会持续产生新内容或对已有内容做修正，负责人需要能够重新运行处理流程而不产生
重复或损坏已有数据。

**Why this priority**: 首次打通链路和规模化验证都基于一次性运行；但项目周期内至少
会补数据或修正错误批次，这个能力不是第一天必需，但短期内会用到。

**Independent Test**: 对已经处理过的一批文档重新触发处理流程（部分文档不变、部分文档
修改、新增少量文档），检查存储中是否仍保持每个来源文档唯一，且新批次标识与旧批次
可以区分。

**Acceptance Scenarios**:

1. **Given** 已处理过的一批文档中有一部分内容被更新，**When** 重新触发处理流程，
   **Then** 对应文档记录的内容与挖掘结果被新批次的结果覆盖或更新，而不产生同一来源
   文档的重复记录。
2. **Given** 一批新增文档与已处理过的文档混合输入，**When** 触发处理流程，**Then** 已
   处理过的未变更文档不会被判定为新增，新增文档正确产出对应记录。

### Edge Cases

- 单条原始文档缺少必填字段（如没有正文或没有原文链接）时，该文档应被标记为无效并
  跳过写入，而不是导致整批处理失败。
- 两个来源提供内容几乎完全相同的文档（例如同一篇论文的预印本与正式版摘要）时，
  去重逻辑如何判定是否为重复，需要有明确、可复现的判定依据（而非人工判断）。
- 单条文档正文过短（如仅几个词）导致关键词抽取或主题聚类结果不可靠时，如何标注
  这条记录的挖掘结果质量，供下游功能决定是否使用。
- 处理过程中某条文档解析或计算失败（不是数据源问题，而是处理本身出错）时，本次
  运行应记录该文档为失败并继续处理其余文档，而不是让整个批次运行中断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须能从 Stack Exchange 多站点技术问答与 arXiv CS 标题/摘要元数据
  两类来源采集原始数据。
- **FR-002**: 系统必须将两类来源的原始数据统一为同一种文档结构，字段至少包含：文档
  唯一标识、来源类型、来源站点/分类、标题、清洗后正文、原始正文、标签、语言、创建
  时间、原文链接、许可证信息、质量标记、处理批次标识。
- **FR-003**: 系统必须对文档正文执行清洗（去除无关标记、统一格式）与跨来源去重，
  去重判定依据必须是可复现的规则或计算结果，而非人工判断。
- **FR-004**: 系统必须为每条有效文档抽取一组带权重的高相关关键词（数量可配置，即
  "取前 k 个"）。
- **FR-005**: 系统必须将每条有效文档归入一个主题簇，并记录该文档所属的簇标识。
- **FR-006**: 系统必须能够计算文档之间的相似度，作为挖掘结果的一部分保留。
- **FR-007**: 系统必须将统一后的文档记录与对应的挖掘结果（关键词、主题簇、相似度
  相关数据）分别持久化到两类可查询的存储集合中，且二者可通过文档标识互相关联。
- **FR-008**: 系统必须支持先以两个来源各 100 条文档的小规模输入完整跑通处理流程，
  验证通过后再扩展到不少于 10,000 条有效文档的规模。
- **FR-009**: 每次处理运行必须生成一个批次标识，所有本次运行产出的文档与挖掘结果
  记录都必须携带该批次标识，用于追溯是哪一次运行、使用了哪个版本的处理逻辑产出的。
- **FR-010**: 每次处理运行必须留存可读的运行记录（起止时间、输入条数、成功产出条数、
  跳过或失败条数），作为可核查的处理证据。
- **FR-011**: 单条文档在采集、清洗或挖掘阶段发生的失败，不得导致整批处理运行中断；
  系统必须记录该条文档的失败原因并继续处理剩余文档。
- **FR-012**: 系统必须支持对已处理过的来源文档重新运行处理流程：内容未变的文档不重复
  产出记录，内容已变的文档以新批次结果更新，不产生同一来源文档的重复记录。
- **FR-013**: 核心的清洗、去重、关键词抽取、主题聚类与相似度计算逻辑必须由批处理
  计算框架执行并留有可检查的执行证据（不得由无过程记录的临时脚本或人工步骤替代）。
- **FR-014**: 文档记录与挖掘结果的持久化必须落地在真实的、可结构化查询的文档型
  存储中（不得以本地文件列表冒充）。

### Key Entities

- **文档（document）**：统一后的单条内容记录，代表一条来自 Stack Exchange 或 arXiv
  的问答/论文摘要，包含来源信息、正文内容、元数据和质量标记，是后续挖掘和展示的
  基本单位。
- **挖掘结果（mining result）**：与某条文档一一对应的处理产出，包含该文档的关键词
  集合、所属主题簇、相似度相关信息，以及产出该结果的批次标识。
- **处理批次（batch）**：一次处理运行的标识，关联本次运行涉及的处理逻辑版本、
  起止时间和处理统计，用于追溯任意一条文档/挖掘结果记录的产出来源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用两个来源各 100 条原始文档作为输入，可以在一次运行内产出对应的
  200 条文档记录和 200 条挖掘结果记录，且每条挖掘结果都包含非空关键词与主题簇归属。
- **SC-002**: 使用不少于 10,000 条有效原始文档作为输入，处理运行可以完整执行完毕
  并产出全部有效文档对应的记录，无需人工中途干预。
- **SC-003**: 对任意一条已产出的文档或挖掘结果记录，都能在 1 分钟内通过其批次标识
  追溯到产出它的那次处理运行的起止时间和处理统计。
- **SC-004**: 重复处理同一批未变更的来源文档时，不会产生重复的文档记录；变更后的
  文档重新处理后，其记录能反映最新内容而不是遗留旧版本。
- **SC-005**: 单条文档处理失败时，该次运行仍能完成剩余全部文档的处理，运行结束后
  失败文档的数量和原因是可读的。

## Assumptions

- 两个来源在本功能范围内均视为只读输入：本功能不负责向 Stack Exchange 或 arXiv
  写回任何数据。
- "有效文档"指字段完整、可解析、非纯重复的文档；不满足这些条件的原始记录在统计
  规模时不计入有效数量。
- 关键词抽取的"数量可配置"在本阶段只要求存在一个可调整的上限参数，具体默认值
  由实施阶段决定，不在本功能范围内固定。
- 主题簇的数量在本阶段视为一个可调整的运行参数，具体取值由实施阶段基于数据规模
  决定，不在本功能范围内固定。
- 本功能不负责根据挖掘结果做个性化判定（known/refine/new/possible_conflict），
  那是下游"个性化知识分类"功能的范围；本功能只保证挖掘结果字段可用。
- 本功能不负责对外提供查询接口（如 HTTP API），那是下游"Web API"功能的范围；
  本功能只保证数据落地在可查询的存储中。
