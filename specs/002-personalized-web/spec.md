# Feature Specification: 个性化知识分类与 Web 展示

**Feature Branch**: `002-personalized-web`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "个性化知识分类与 Web API/交互页面功能。基于 Feature 1（数据管道与 Spark 挖掘）产出的 documents 和 mining_results 集合，构建个性化知识分类与展示层：新增 user_profiles（用户已知主题、已读文档、反馈）和 user_knowledge（用户对每个知识单元的掌握状态与判定依据）两个 MongoDB 集合；对每个知识单元（TF-IDF 关键词/主题簇，而非整篇文档）结合关键词级精确匹配和 KMeans 主题簇级匹配，判定为 known/refine/new/possible_conflict 四种状态之一，possible_conflict 必须附带可追溯证据并要求人工复核；提供 Flask 只读+画像更新 API：GET /api/topics、GET /api/documents/{id}、GET /api/recommendations?user_id=&limit=、POST /api/profile/topics、POST /api/profile/feedback；提供单页 Web，包含已知主题选择、新知识/深化知识推荐列表、来源筛选（Stack Exchange/arXiv）、关键词与评分依据展示、数据规模与 Spark 批次信息展示；无真实用户行为数据时，使用显式主题选择加人工标注评估 Precision@K/NDCG 相对非个性化基线的提升；第一技术切片先用小规模数据（如 Feature 1 的 100+100 条切片结果）打通用户画像录入 → 分类判定 → API → 页面的全链路，再扩展到 Feature 1 产出的完整规模数据。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 打通画像到页面的最小垂直切片（Priority: P1）

用户需要先设置自己已经掌握的主题，然后在页面上看到一份基于该画像生成的"新知识/
深化知识"推荐列表，并能看到每条推荐为什么被这样分类。

**Why this priority**: 这是整个个性化展示层价值的最小闭环。如果画像设置之后推荐
列表和判定依据都出不来，后面的规模化和评价工作都没有意义。

**Independent Test**: 使用 Feature 1 第一技术切片产出的 100+100 条挖掘结果作为
输入，设置一个包含若干已知主题的用户画像，请求该用户的推荐结果，检查返回的每条
结果是否都带有判定状态（known/refine/new/possible_conflict 之一）与可读的判定
依据。

**Acceptance Scenarios**:

1. **Given** Feature 1 已产出的一批文档与挖掘结果，**When** 为一个新用户设置若干
   已知主题，**Then** 系统为该用户生成的每个知识单元判定都能在已知主题集合与主题
   簇归属之间找到对应关系，而不是随意结果。
2. **Given** 已设置画像的用户请求推荐列表，**When** 页面加载完成，**Then** 页面
   展示该用户的新知识/深化知识推荐，每条推荐可见来源文档、涉及关键词，以及判定为
   该状态的依据。
3. **Given** 一个从未设置任何已知主题、也没有已读文档记录的新用户，**When** 该用户
   请求推荐列表，**Then** 该用户的全部知识单元被判定为 new，页面正常展示而不是
   报错或空白。

### User Story 2 - 规模化判定与效果评价（Priority: P2）

课程评审者/教师需要看到个性化判定在不少于 10,000 条数据规模下完整跑通，并需要
证据证明"个性化推荐"确实比"不做个性化的固定排序"更贴合用户已知情况。

**Why this priority**: 只有在最小垂直切片（P1）验证判定逻辑本身正确之后，扩大到
全量规模并做效果对比才有意义；这是课程评分中"提升"与"可评价"部分的核心证据来源。

**Independent Test**: 对 Feature 1 产出的全量规模挖掘结果，批量完成个性化判定，
构造至少两个不同的模拟用户画像，人工标注推荐结果的相关性，并计算个性化排序与
非个性化固定排序基线之间的对比指标。

**Acceptance Scenarios**:

1. **Given** 不少于 10,000 条有效文档对应的挖掘结果，**When** 触发批量个性化判定，
   **Then** 全部知识单元都产出对应的判定状态，过程无需人工逐条介入。
2. **Given** 至少两个显式设置的模拟用户画像与对应的人工相关性标注，**When** 分别
   计算个性化推荐与非个性化固定排序基线的效果指标，**Then** 可以得到两组可比较
   的数值结果，用于判断个性化排序是否优于基线。

---

### User Story 3 - 反馈闭环与画像演进（Priority: P3）

用户在查看推荐结果后可以标记反馈（如确认已经掌握、标记为有用/无关），系统据此
更新该用户的知识画像，使后续推荐随之调整。

**Why this priority**: 首次打通链路和规模化评价都建立在静态画像之上；反馈闭环
让个性化机制显得可持续演进，但不是最小闭环必需的第一步，可以在前两步稳定后补上。

**Independent Test**: 对一个已有画像和历史推荐记录的用户提交一条反馈（如将某条
被判定为 new 的知识单元标记为"已经掌握"），重新请求该用户的推荐列表，检查对应
知识单元及其相关内容的判定状态是否发生了预期变化。

**Acceptance Scenarios**:

1. **Given** 用户收到一条判定为 new 的推荐，**When** 用户提交"已经掌握"的反馈，
   **Then** 该用户的已知主题或已读记录被更新，后续涉及相同关键词/主题簇的知识
   单元判定状态发生相应变化（如变为 known 或 refine）。
2. **Given** 用户对同一条知识单元先后提交了矛盾的反馈，**When** 系统处理反馈，
   **Then** 画像以最近一次反馈为准更新，不保留旧反馈造成的矛盾状态。

### Edge Cases

- 用户没有设置任何已知主题、也没有已读文档记录时，所有知识单元应判定为 new，
  而不是报错或返回空结果。
- 知识单元被判定为 possible_conflict 但系统找不到可追溯的判定证据（如具体的
  冲突片段引用）时，必须降级为 new 或 refine，不得展示无依据的冲突提示。
- 某个主题簇内文档数量极少（如只有 1 篇）时，该簇作为"已知主题"选项展示会导致
  用户几乎无法再命中任何新内容，需要有合理的处理方式（如仍展示但不作为主要推荐
  依据来源）。
- 未登录状态下尝试访问个人知识画像、推荐结果或提交反馈时，系统必须拒绝并提示需要
  登录，而不是返回默认数据或导致页面崩溃。
- 已登录用户尝试通过修改请求参数（如更换用户标识）访问或修改其他用户的知识画像、
  推荐结果或反馈时，系统必须拒绝该请求。
- 分页/数量参数无效（如负数）时，系统必须返回明确的错误提示，而不是返回错误数据
  或导致页面崩溃。
- 请求按来源筛选（Stack Exchange / arXiv）但某一来源在当前数据规模下几乎没有
  数据时，页面需要明确提示"该来源暂无更多结果"，而不是显示为加载失败。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须针对每个知识单元（文档中抽取出的关键词或该文档所属的主题簇，
  而非整篇文档）为指定用户判定 known、refine、new、possible_conflict 四种状态
  之一。
- **FR-002**: 判定必须同时结合两层信号：知识单元与用户已知关键词集合的直接匹配
  程度，以及知识单元所属主题簇是否命中用户已读文档所在的主题簇集合。
- **FR-003**: possible_conflict 状态只能在系统能提供可追溯的判定证据（如具体的
  冲突片段引用）时产生；无法提供该证据时必须降级为 new 或 refine。
- **FR-004**: 系统必须提供账户注册与登录机制；用户在访问个人知识画像、推荐结果
  或提交反馈前必须先完成登录验证身份。
- **FR-005**: 系统必须确保已登录用户只能查看和修改自己的知识画像、推荐结果与
  反馈记录；即使请求中携带其他用户的标识，也必须拒绝访问或修改他人数据。
- **FR-006**: 系统必须允许已登录用户显式设置和修改自己的已知主题集合。
- **FR-007**: 系统必须记录用户已读过的文档，并将其纳入该用户知识画像用于后续
  判定。
- **FR-008**: 系统必须提供可查询的推荐结果：按已登录用户返回其当前的新知识/深化
  知识推荐列表，每条结果包含来源文档、涉及的知识单元、判定状态，以及判定依据
  （命中的关键词或主题簇）。
- **FR-009**: 系统必须提供可查询的主题列表，展示当前已挖掘出的主题簇及其代表
  关键词，供用户在设置已知主题时选择；该查询不涉及用户个人数据，无需登录。
- **FR-010**: 系统必须支持按文档标识查询单条文档详情及其对应的挖掘结果；该查询
  不涉及用户个人数据，无需登录。
- **FR-011**: 系统必须允许已登录用户对某条推荐结果提交反馈（如确认已掌握、标记
  有用、标记无关），并将该反馈纳入该用户知识画像的更新。
- **FR-012**: 系统必须提供一个可交互的页面，让用户完成注册/登录、已知主题选择、
  查看推荐列表、按来源筛选结果、查看关键词与判定依据，且用户无需查看原始数据
  存储或直接调用底层查询接口。
- **FR-013**: 当已登录用户没有设置任何已知主题且没有已读文档记录时，系统必须将
  该用户的全部知识单元判定为 new。
- **FR-014**: 系统必须能对不少于 Feature 1 产出规模（不少于 10,000 条有效文档）
  的全部知识单元完成判定，过程无需人工逐条介入。
- **FR-015**: 在缺乏真实用户行为数据的情况下，系统必须支持通过显式主题设置构造
  至少两个不同的模拟用户画像（对应真实注册账户），并支持人工对其推荐结果进行
  相关性标注，用于计算评价指标。
- **FR-016**: 系统必须能够计算个性化推荐相对于"不做个性化、按固定规则排序"基线
  的效果对比指标（如 Top-K 相关性或等价的命中率指标），并使结果可供查看。
- **FR-017**: 系统必须先以 Feature 1 第一技术切片产出的小规模数据（两来源各 100
  条对应的挖掘结果）打通"注册/登录 → 画像录入 → 判定 → 查询接口 → 页面展示"全
  链路，验证通过后才能扩展到 Feature 1 的全量规模数据。
- **FR-018**: 系统必须支持按来源（Stack Exchange / arXiv）筛选展示的推荐结果。
- **FR-019**: 用户对同一知识单元先后提交矛盾反馈时，系统必须以最近一次反馈为准
  更新画像，不得保留造成矛盾的旧状态。

### Key Entities

- **知识单元（knowledge unit）**：从某篇文档中抽取出的关键词或该文档所属的主题
  簇，是个性化判定的最小粒度；同一篇文档可以同时包含对某用户已知和未知的知识
  单元。
- **用户知识画像（user profile）**：用户显式设置的已知主题集合、已读文档列表与
  反馈历史的集合，代表该用户当前的知识边界，随反馈不断更新。
- **知识单元判定记录（user knowledge judgement）**：特定用户对特定知识单元的
  判定状态（known/refine/new/possible_conflict）及判定依据（命中的关键词或
  主题簇、必要时的冲突证据片段），会随用户画像更新而重新计算。
- **推荐结果条目（recommendation item）**：面向某用户展示的一条条目，关联来源
  文档、涉及的知识单元、判定状态与依据，是页面和查询接口的最终输出单位。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用 Feature 1 产出的 100+100 条切片数据，用户设置任意已知主题后，
  可在页面上看到对应的新知识/深化知识推荐列表，且每条结果都能看到判定依据。
- **SC-002**: 对不少于 10,000 条有效文档对应的挖掘结果，个性化判定可以完整批量
  完成，无需人工逐条介入。
- **SC-003**: 通过至少两个模拟用户画像的人工标注评估，可以得到个性化推荐排序与
  非个性化固定排序基线的可比较效果数据，用于判断个性化排序是否优于基线。
- **SC-004**: 用户修改已知主题或提交反馈后，再次查询推荐结果时，相关知识单元的
  判定状态能反映最新画像（例如新增已知主题后，原先的 new 状态可能变为 known 或
  refine）。
- **SC-005**: 出现 possible_conflict 判定状态时，页面必须展示支持该判定的可追溯
  证据；如果没有该证据，系统不会展示 possible_conflict 状态。
- **SC-006**: 用户能够在不查看任何原始数据存储或代码的情况下，完成已知主题选择、
  查看推荐结果、按来源筛选的完整操作流程。

## Assumptions

- 本功能依赖 Feature 1（数据管道与 Spark 挖掘）已产出的文档与挖掘结果数据存在且
  字段完整；本功能不重新执行采集或挖掘计算，只消费其产出的关键词、主题簇归属和
  相似度数据。
- 项目周期内没有真实的多用户线上行为数据；评价个性化效果时使用显式主题设置模拟
  的用户画像加人工相关性标注，而不依赖真实点击/停留行为日志。
- "用户"在本功能范围内指注册并登录的真实账户，每个账户关联一份个人知识画像；
  认证鉴权采用课程项目适用的标准实现（如邮箱/用户名+密码，会话或 Token 方式），
  具体技术选型由实施阶段决定，不要求达到生产级安全合规标准（如多因素认证、密码
  找回全流程）。
- 判定为 possible_conflict 所需的"可追溯证据"是指能定位到具体文档片段或关键词
  的引用，而非笼统的"可能存在冲突"提示语。
- 主题簇的代表关键词（用于主题选择页面展示）由 Feature 1 挖掘结果中每个主题簇内
  高权重关键词聚合得到，具体聚合方式由实施阶段决定。
- 页面与查询接口的性能、并发规模遵循标准课程演示场景（单人或几人同时访问），
  不需要满足生产级高并发要求。
