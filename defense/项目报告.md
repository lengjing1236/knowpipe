# 基于 Spark 与 MongoDB 的多源技术内容知识挖掘与个性化发现系统 —— 项目报告

> 本报告依据课程要求"项目报告须含系统架构、技术选型、功能说明、组内分工与贡献说明"撰写，
> 内容严格来自 SDD 过程文档：`.specify/memory/constitution.md`、
> `specs/001-data-pipeline-spark-mining/*`、`specs/002-personalized-web/*`、
> `evidence/*/acceptance-record.md`。

## 1. 系统架构

本项目按课程要求的四层架构组织，拆分为两个 SDD Spec 递进实现：

| 层次 | 职责 | 本项目实现 | 所属 Spec |
|---|---|---|---|
| 交互层 | 用户交互、业务操作、可视化输出 | Flask 服务端渲染页面（登录/主题选择/推荐列表），原生 JS `fetch` 调用后端 API | Feature 2 |
| 业务逻辑层 | 承接前端请求、封装业务功能、调度数据与挖掘接口 | Flask Blueprint 路由（`routes_api.py`）、session 鉴权（`auth.py`）、分类判定规则（`classify.py`） | Feature 2 |
| 数据管理与挖掘层 | 按数据类型匹配存储模型，完成存储/检索/管理/分析挖掘 | MongoDB 集合设计与索引、读写与聚合查询（`mongo_sink.py`） | Feature 1 + Feature 2 |
| 大数据底层处理层 | 大规模数据分布式存储与计算 | PySpark DataFrame + MLlib：TF-IDF、KMeans、相似度、推荐分数（`spark_job.py`、`score_job.py`） | Feature 1 + Feature 2 |

两个 Spec 的边界严格分离：Feature 1（`001-data-pipeline-spark-mining`）负责数据采集到
MongoDB 落库的完整挖掘链路；Feature 2（`002-personalized-web`）在其产出之上做个性化判定
与 Web 展示，**只读**查询 Feature 1 的 `documents`/`mining_results` 集合，不修改其结构，
不导入其内部实现，唯一显式复用的是 `knowpipe/mining/batch.py` 的批次证据结构
（`BatchStats`/`new_batch_id`），保证两个 Spec 的运行批次统一落在同一套 `batches` 集合中
可追溯。该只读边界已通过代码审计确认：`knowpipe/web/*.py` 中未出现任何对
`documents`/`mining_results` 的写操作，仅通过查询接入。

## 2. 技术选型

项目宪法（`.specify/memory/constitution.md`）明确规定了不可替代的技术边界，指导了以下选型：

- **批处理引擎：Spark（PySpark + MLlib）**，不使用 Flink/Kafka —— 挖掘任务是一次性批量
  计算而非流式处理，且课程要求核心计算必须真实运行在 Spark 上并留有可检查证据。
- **存储：MongoDB**，不使用图数据库/键值存储/时序数据库 —— 技术内容（问答、论文摘要）
  是半结构化数据，字段随来源略有差异，MongoDB 的灵活 schema 与文档模型契合度最高。
- **鉴权：Flask 内置 `session` + Werkzeug `generate_password_hash`/`check_password_hash`**，
  未引入 Flask-Login 或 JWT —— 项目不要求生产级安全合规（无 MFA/限流需求），现有依赖已能
  满足"真实登录、真实会话隔离"的要求，额外框架属于过度设计。
- **单元测试替身：mongomock**，仅用于快速反馈的单元测试；规模验收（≥10,000 条 / 5 步
  quickstart）必须对接真实 MongoDB 实例与真实 `local[*]` SparkSession —— 项目宪法明确
  "mongomock 不能替代验收证据"。

项目宪法同时明确禁止以下简化替代方案，以保证展示的是真实大数据组件而非模拟实现：
"用线程池模拟 Spark 计算""用本地 JSONL/SQLite 顶替 MongoDB""用 CLI 输出或 Markdown 报告
顶替 Web 展示"。

## 3. 功能说明

### 3.1 Feature 1：数据管道与 Spark 挖掘

**目标**：从 Stack Exchange（技术问答，主源，四站点 stackoverflow / serverfault /
superuser / askubuntu 轮换采集）与 arXiv CS（论文摘要，补充源）采集技术内容，经 Spark
完成清洗、去重、TF-IDF 关键词抽取、KMeans 主题聚类、文档间相似度计算，写入 MongoDB。

**关键设计**：
- 去重采用两级判定：精确去重（`source + source_url` 相同 → upsert 覆盖）+ 近似去重
  （清洗后标题+正文 SHA-256 哈希相同 → 跳过），保证判定依据可复现，不依赖人工阈值调参。
- 单条文档校验失败在进入 Spark 计算前的清洗阶段过滤，不依赖 Spark DataFrame 算子做
  逐行容错（DataFrame API 本身不支持这种细粒度容错语义）。
- `mining_results` 集合按批次追加历史记录，同一文档重新挖掘后旧结果不删除，
  `documents.mining` 字段只维护指向最新批次的摘要引用，保证任意历史批次可追溯。

**规模化过程中的真实问题与修复**（详见 `evidence/001-data-pipeline-spark-mining/acceptance-record.md`）：
1. **性能缺陷**：同簇相似度两两比较原为 Spark driver 端的纯 Python O(簇大小²) 循环，
   KMeans 分簇不均衡（簇数设为 64，实测仍聚成 5 个大簇），数据量达 10500 条时进程被系统
   杀死。修复为对超过阈值（300）的簇先用一次小规模 Spark KMeans 递归拆分成有界子组再
   两两比较，不改变落库的 `topic_cluster_id`。修复后 3000 条耗时 103 秒、10500 条耗时
   240 秒，均可正常完成。
2. **数据完整性缺陷**：Stack Exchange 的 `question_id` 仅在单站点内唯一，但四个站点的
   `source` 字段值均为常量 `"stackexchange"`，导致跨站点撞号后静默覆盖（真实运行观察到
   11 条）。修复为 `doc_id` 增加站点前缀（如 `serverfault-12345`），保证全局唯一。
3. **运行记录完整性**：`spark_job.main()` 原实现在异常发生于写入 `batches` 集合之前时会
   丢失运行统计。修复为异常路径也落盘 `status="failed"` 与错误信息，并将校验失败原因、
   采集重试失败原因通过标准 `logging` 模块记录，不再静默。

**验收现状**：环境验证（PySpark 4.2.0、Java 17、MongoDB 7.0.14 真实实例）全部通过；
100+100 条最小链路（`batch_id: 20260905-7442679d`）与幂等更新（3 个测试用例）验收完成；
≥10,000 条规模化验收因当日 Stack Exchange API 配额耗尽（差 4 条未达标）及随后触发的
限流封锁，标注为"待补充"，已用修复后代码验证性跑通 9,986 条，确认两处修复均生效，
待封锁解除后将重跑最终批次。全部 35 个单元测试通过。

### 3.2 Feature 2：个性化知识分类与 Web 展示

**目标**：基于 Feature 1 产出的关键词与主题簇，将其拆解为更细粒度的"知识单元"，为每个
注册用户判定 `known`（已知）/ `refine`（需深化）/ `new`（全新）/ `possible_conflict`
（疑似冲突）四态，并提供鉴权 API 与 Web 页面展示个性化推荐。

**核心架构取舍**：分类判定与推荐分数计算被拆分到不同技术栈：
- **分类判定**（四态判定）：纯 Python 规则函数（`classify.py`），不经 Spark。理由：判定
  结果依赖单个用户画像，用户修改已知主题的频率远高于底层文档规模变化频率，若强制用 Spark
  对全量文档×全量用户做批处理，每次画像变更都要重跑 Spark 作业，与"修改画像后判定状态
  实时反映"的要求冲突；项目宪法要求必须用 Spark 计算的四类核心内容（TF-IDF、KMeans、
  相似度、推荐分数）不包含分类判定本身。
- **推荐分数**：PySpark DataFrame 批量计算（`score_job.py`），公式为
  `score = α×主题相关度 + β×新增关键词比例 + γ×文档质量 - ε×已读惩罚`（来源多样性项因
  两来源数据规模差异较大，为避免分数被数据量而非内容质量主导，决策暂不计入）。该计算不
  依赖具体用户，可作为全量批处理复用给所有用户。

**数据模型**：`users`（账户）/ `user_profiles`（`known_topics`/`known_keywords`/
`read_doc_ids`/`feedback_history`）/ `user_knowledge`（`user_id + knowledge_id` 复合
唯一索引，`knowledge_id` 格式为 `kw:{term}` 或 `topic:{topic_cluster_id}`，仅保留每个
用户对每个知识单元的最新判定）。`possible_conflict` 状态要求同时存在非空
`conflict_evidence` 且 `pending_review=false`（人工复核通过）才对外可见，复核前一律
降级展示为 `new`/`refine`。

**API 与鉴权**：8 个接口契约（注册/登录/登出/主题列表/文档详情/推荐/画像更新/反馈提交），
4 个公开、4 个需登录。鉴权采用 Flask session：未登录访问需登录接口返回 401；session 有效
但请求了他人的 `user_id` 返回 403（越权直接拒绝，不静默按 session 用户改写）。推荐接口
支持 `mode=personalized|baseline` 切换，`baseline` 模式（无已读记录时按最新时间倒序、
有已读记录时按 `similar_doc_ids` 相似度排序）不返回判定字段，用于与个性化结果对比。

**验收现状**：全部基于真实 MongoDB（Feature 1 产出的 200 篇文档/210 条挖掘结果）与真实
`local[*]` Spark 完成 5 步 quickstart 验证：最小链路全链路打通、新用户默认全部 `new`、
未登录 401/越权 403、反馈提交后状态实时联动变化（`kw:allocator` 由 `new` 变为 `known`）、
推荐打分作业运行（`batch_id: 20260905-97b399c7`）后个性化与基线两组结果呈现明显差异。
全部 5 步通过，全仓库 88 个测试（含 Feature 1）全部通过。规模化验收基于 Feature 1 当前
实际产出规模（200 篇文档），待 Feature 1 最终万级批次产出后可直接复用同一套代码重跑，
无需改动 Feature 2 代码。
