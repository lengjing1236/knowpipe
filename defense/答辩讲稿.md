## 第 6 页：项目宪法核心原则（约束两个 Spec 的红线）

**内容**：
- **Principle I（不可协商）**：核心挖掘计算——TF-IDF、KMeans 主题聚类、相似度、推荐分数——
  必须由 Spark 可复现程序产出，并留有可检查证据（日志/条数/耗时）；LLM 只能做推荐理由
  润色、"疑似冲突"候选生成等辅助环节，不能替代核心计算结果。
- **Principle II**：分类判定的对象是从文档拆解出的"知识单元"（关键词/主题簇），不是整篇
  文档；每次判定必须可追溯到具体依据（命中的关键词集合、命中的主题簇 id）；`possible_conflict`
  必须有可追溯证据，且经人工复核后才对用户可见。

**讲稿**：
"整个项目最核心的两条硬性约束写在项目宪法里。第一条是 Spark 计算边界：关键词提取、主题
聚类、相似度、推荐打分这四类核心计算必须真实跑在 Spark 上，AI 大模型只能做锦上添花的
辅助，不能拿 AI 生成的结果冒充大数据计算成果。第二条是可追溯性：我们判定一个知识点用户
是"已知"还是"全新"，必须能说出具体命中了哪些关键词或主题簇，不能是黑箱结论；'疑似冲突'
这种敏感判定还必须经过人工复核才能展示给用户。"

## 第 8 页：Feature 1 —— MongoDB 数据模型

**内容**：
- `documents` 集合：`doc_id` / `source`(stackexchange\|arxiv) / `title` / `body_text` /
  `quality`(短文本判定、去重哈希) / `batch_id`；唯一索引 `source + doc_id`
- `mining_results` 集合：`doc_id` / `batch_id` / `keywords`[{term, weight}] /
  `topic_cluster_id` / `similar_doc_ids` / `reliable`；索引 `doc_id + batch_id`，
  **同一文档跨批次的历史结果保留、不覆盖**
- `batches` 集合：`batch_id`（`{日期}-{哈希}`格式）/ `started_at` / `finished_at` /
  `input_count` / `valid_count` / `failed_count`，保证任意一次运行可在秒级被追溯

**讲稿**：
"存储设计上有一个关键决定：mining_results 按批次追加历史记录，同一篇文档如果被重新挖掘，
旧的结果不会被删除，而是保留下来，documents 里只维护一个指向最新批次的摘要引用。这样设计
是为了让每一次挖掘运行都可追溯、可对比，配合 batches 集合记录的运行统计，任何时候都能
查到某次批次处理了多少条、成功多少、失败多少。"

## 第 9 页：Feature 1 —— 遇到的问题与修复（真实规模化过程）

**内容**（两个真实的"发现问题→分析→解决"案例）：

1. **性能缺陷**：同簇相似度两两比较是 O(簇大小²) 的纯 Python 循环，KMeans 不保证簇大小
   均衡（簇数调到 64，实测仍聚成 5 个大簇），10500 条时进程被系统杀死。
   → 修复：超过阈值（300）的簇先用小规模 Spark KMeans 递归拆分成有界子组再比较，不改变
   落库的 `topic_cluster_id`。修复后 3000 条耗时 103s、10500 条耗时 240s，均可正常跑完。
2. **数据完整性缺陷**：Stack Exchange 的 `question_id` 只在单站点内唯一，但四个站点的
   `source` 字段都是常量 `"stackexchange"`，跨站点撞号导致 11 条记录被静默覆盖。
   → 修复：`doc_id` 加站点前缀，如 `serverfault-12345`，保证全局唯一。

**讲稿**：
"规模化过程中我们真实遇到并解决了两个问题。第一个是性能问题：相似度比较原来是在 Spark
driver 端用纯 Python 循环两两比较，而 KMeans 分出来的簇大小很不均衡，导致数据量上去后
时间呈平方级增长，跑到一万条规模时进程直接被系统杀掉。我们的修复是把超大的簇再做一次
小范围聚类拆分成有界子组，只在子组内比较，不影响最终落库的主题簇编号。第二个是数据完整性
问题：Stack Exchange 不同站点的问题 ID 是各自独立编号的，但我们最初把 source 字段写成
了统一的常量，导致跨站点的 ID 冲突互相覆盖，真实运行中发现了 11 条这样的记录，我们通过
给 doc_id 加站点前缀解决。"

## 第 12 页：Feature 2 —— 核心架构取舍：分类判定为什么不用 Spark

**内容**：
- **分类判定**（known/refine/new/possible_conflict）：纯 Python 规则函数，不经 Spark
- **推荐分数**（score）：PySpark DataFrame 批量计算，公式：
  `score = α×主题相关度 + β×新增关键词比例 + γ×文档质量 - ε×已读惩罚`
- **理由**：分类判定依赖单个用户的画像，用户画像变化频率远高于文档规模变化；若强制用
  Spark 对全量文档×全量用户做批处理，用户每次修改已知主题都要重跑 Spark 作业，与"修改画像
  后判定状态实时反映"的要求冲突。宪法 Principle I 的强制清单是 TF-IDF/KMeans/相似度/
  推荐分数四项，分类判定不在其中。

**讲稿**：
"这里有一个值得展开的架构决策。分类判定我们用的是纯 Python 规则函数，没有经过 Spark；
但推荐分数是真正跑在 PySpark 上的批处理任务。为什么这样拆？因为分类判定是针对单个用户
的实时操作——用户在页面上勾选一个新的已知主题，判定结果要立刻更新，如果这一步也要启动
一次 Spark 作业，响应会变得很慢，而且用户画像的变化频率远高于底层文档规模的变化频率。
而推荐分数不依赖具体某个用户，是对全量文档批量计算一次就能复用的，所以适合用 Spark。
项目宪法里明确列出必须用 Spark 的四类核心计算——关键词、主题聚类、相似度、推荐分数——
分类判定不在这个清单里，所以这个拆分是被允许的。"

## 第 13 页：Feature 2 —— 数据模型与状态机

**内容**：
- `users` / `user_profiles`（`known_topics`/`known_keywords`/`read_doc_ids`/
  `feedback_history`）/ `user_knowledge`（`user_id + knowledge_id` 复合唯一索引，
  `knowledge_id` 格式为 `kw:{term}` 或 `topic:{id}`）
- **状态机**：
  ```
  关键词/主题簇均未命中           → new
  命中主题簇且有明显新增内容      → refine
  关键词高度重合                  → known
  检测到疑似语义冲突 + 人工复核通过 → possible_conflict（复核前对外仍显示 new/refine）
  ```

**讲稿**：
"数据模型上，user_knowledge 集合是核心，每条记录对应一个用户对一个知识单元的判定，
knowledge_id 的格式区分关键词类和主题簇类。判定逻辑是一个四态状态机：完全没接触过的
判定为全新；接触过对应主题但有明显新内容的判定为需深化；关键词高度重合的判定为已知；
疑似冲突这一状态比较特殊，即使系统检测到了，也必须经过人工复核确认后才会展示给用户，
复核之前一律降级显示为全新或需深化，这是为了保证冲突提示的可信度。"

## 第 14 页：Feature 2 —— API 契约与鉴权模型

**内容**：8 个接口（公开 4 个 / 需登录 4 个）：
- 公开：`POST /auth/register`、`POST /auth/login`、`GET /topics`、
  `GET /documents/{source}/{doc_id}`
- 需登录：`POST /auth/logout`、`GET /recommendations`（含 `mode=personalized|baseline`）、
  `POST /profile/topics`、`POST /profile/feedback`
- **鉴权模型**：Flask session；未登录访问需登录接口 → 401；session 有效但请求了他人的
  `user_id` → 403（越权拒绝，不静默改写）

**讲稿**：
"接口层面我们定义了 8 个契约，一半公开一半需要登录。鉴权用的是 Flask 自带的 session
加 Werkzeug 的密码哈希，没有引入额外的登录框架，因为项目规模不需要那么重。越权保护上
我们的原则是：请求体或参数里的 user_id 一旦和当前 session 里的不一致，直接返回 403
拒绝，而不是静默地按 session 里的用户处理——这样任何越权尝试都会被明确暴露而不是被
悄悄纠正掩盖过去。"
