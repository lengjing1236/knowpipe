# MVP需求到实现的差距复核

日期：2026-09-25。依据：用户最新要求、根plan、008–010规格、当前代码、010实际查询与译文记录。只读复核代码，本轮调整计划；没有新增算法效果结论。

## 结论

MVP尚未通过。已有实现提供词汇检索、历史降重、证据展示及完整工作流的基础，但不能从任务全勾、155项回归通过或8个中文目标非空，推出核心推荐满足用户需求。

需要逐层检查：用户要什么 → Spec如何规定正确结果 → 算法如何产生结果 → 测试是否覆盖 → 真实输出是否满足。Spec本身没有表达必要的产品结果时，即使实现严格遵守Spec，产品仍存在gap。

## 可定位的差距

| 编号 | 产品需求与规格依据 | 实现及现有证据 | gap及下一步验证 |
| --- | --- | --- | --- |
| G1 | 008 US1/FR-004要求围绕目标推荐；010 SC-001仅要求8组目标完成处理并报告 | engine.recommend按词汇相关性、覆盖和名称门槛召回；010操作系统调度返回文件访问脚本 | 运行成功门槛弱于产品相关性。Spec应要求正文能回答/讲解目标问题，加入泛词干扰反例，不能只验证非空 |
| G2 | 008 US2/FR-006用重合降序近似个性化补充；SC-005明确没有标签只报告机制 | engine._choose使用相关性、历史重合惩罚和列表冗余；已有合成历史用例 | 减少重复机制成立，不等于选择对学习有具体补充的资料。需相同目标、不同真实已读覆盖的对照，核验变化理由是否正确 |
| G3 | 用户希望比较材料区别、推荐未覆盖内容；规格将其收缩为有限词汇比较并附局限说明 | supplement_eligible依赖相似度区间、共同词及至少两个额外词；supplement_score用于选解释片段，主排序的compact只接收doc_key/relevance/history_overlap | 明确的需求与算法能力差距。不能只把supplement_score加入主排序就宣称解决，因它仍是词汇代理；先定义具体概念/方法、同义复述和部分补充的可核对结果 |
| G4 | 中文阅读应能理解原知识；010 SC-003允许真实翻译记录失败，FR-005仅要求有限检查 | quality.check_translation检查数字和代码保留；WAL译文通过检查，却将fsync译错；目标翻译也有事务→service | 工程完整性不能验收语义可用。应检查技术对象、关系、否定/条件和数值含义，并区分目标转换失败与阅读翻译失败 |
| G5 | 009 US3要求相关新播客和补充依据 | podcasts.learning.publish_recommendations使用supplement_eligible与中文就绪状态决定通知 | 通知幂等和版本控制不证明推荐应当发生。用实际相关补充、复述、无关三类新内容验证决定；音频转写错误须单列定位 |
| G6 | 用户需要可运行的Web MVP | 010浏览器验收读取真实离线排名后写入临时任务表，检查页面呈现；008/009另有历史流程证据 | 页面测试没有伪造排名，但不足以单独证明最终算法在当前worker→API→Web路径生效。需以当前MVP规格执行实际输入到输出的完整路径 |

这是产品需求/验收强度的复核，并非声称上述代码全部违反各自历史阶段的有限契约。阶段规格中的能力限制应继续保留；新的MVP不能沿用这些弱门槛就宣布通过。

## 验证次序

1. 先写MVP可判定的正确结果及失败反例，不按现有函数反向编写需求。
2. 冻结少量真实多源材料、中文目标、不同已读覆盖和预期依据，运行现有基线；独立于现有词汇分数判断对错。
3. 依据失败原因决定最小改动，保持同一输入和对照；修改必须影响真实召回/排序/通知，而不只是更好看的解释。
4. 在现有万条背景语料和实际Web路径复核；全部声明的MVP必需项有证据后，再决定规模扩展。

补充价值是“相对提供的已读材料、与当前目标相关的具体内容”，不是证明用户此前从未学过，也不是宣称一次推荐提升了长期学习成绩。对这两种更强结论，目前没有证据。
