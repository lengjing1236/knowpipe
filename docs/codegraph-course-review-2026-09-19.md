## 按收益排序的改进

### P0：完成规模和效果闭环

1. **万条有效主源验收。** [方案] 固定原始数据快照和采集来源，完成最新成功批次的有效 Stack Exchange ≥10,000，单独报告 arXiv 数量。保存输入、去重、失败、有效和实际落库条数、开始结束时间、参数、代码版本、Spark application ID 与事件日志。验收时查询真实 MongoDB，并从网页抽查结果；重复执行检查幂等性。采集目标数、两集播客或历史 9,986 条均不能代替该证据。
2. **真实推荐评价。** [已验证] `knowpipe/evaluation/metrics.py` 已实现 Precision@K/NDCG@K，但工具测试不等于业务提升。[方案] 先完成至少两个画像的人工盲标，再视时间扩到 10–20 个画像/任务；合并个性化与基线候选池，记录 0–3 相关性标签、数据批次和画像快照。报告逐任务指标、均值、样本数及标注分歧；扩大样本后再讨论置信区间。不要用排序不同证明推荐更好。
3. **补齐课程交付物。** [课程要求] 第 15 页要求源代码、SDD 与全部 Vibe Coding 提示词、项目报告、≤5 分钟 MP4 备份视频、最终分工表、评优组 PPT。[已验证] 当前 Git 跟踪列表未发现 MP4 或以“分工”命名的独立文件，这不证明外部材料不存在。[待确认] 核对外部交付位置和最终分工；如需补录提示词或贡献说明，应明确回顾整理的来源，避免冒充同期记录。

### P1：修正扩展瓶颈和模型一致性

| 源码依据 | 影响 | 改进与验收标准 |
|---|---|---|
| `mining/spark_job.py:run_mining` 收集全部特征到 driver，再创建有界候选组并分发 Spark task | [已验证] 相似度在 task 执行，但 driver 内存仍随输入增长；组间邻居可能漏召回 | [方案] 特征保留在 DataFrame，比较分布式候选 join / LSH；用小规模精确检索测 Recall@K，在 1k/10k/更大切片记录内存、shuffle、耗时与质量 |
| `web/score_job.py:_collect_rows` 嵌套遍历用户和知识单元，每次查询文档及其结果，并积累全部输入行 | [已验证] 查询次数随用户数 × 单元数增长；已有 500 文档分块读取未覆盖该循环 | [方案] 先批量提取文档质量和当前批次映射，复用画像与特征，逐步改为分布式 join；以 Mongo 查询次数、driver 内存和评分吞吐量验收 |
| `web/mongo_sink.py:get_topic_aggregations` 按簇编号聚合，`classify.py` 直接匹配画像中的编号 | [已验证] 编号自身不包含模型版本；若混合不同重训练批次，不能保证同编号同语义 | [方案] 增加模型版本及词表版本，采用版本化主题键和原子发布的有效快照；用两次训练及部分更新验证画像不会静默匹配错误主题 |
| `score_job` 为独立手动入口，画像更新后分数可能未刷新 | [已验证] 分类可更新而排序仍使用旧分数 | [方案] 标记画像版本和评分版本，通过持久任务重新评分；页面暴露更新时间，测试画像修改与评分失败后的行为 |
| `podcasts/feeds.py:parse_transcript` 复杂度 24，`parse_feed` 为 20 | [已验证] 格式兼容、内容校验集中于单个函数 | [方案] 按 JSON/VTT/HTML/文本拆分解析器，保留统一验证；回归真实文字稿样例、错误格式和安全边界 |

[方案] 为真实 Mongo 集成、Spark 单元回归和 Web/API 测试建立 CI；先固定 Python/Java/依赖环境，再验证 Docker 的 web/worker 两个构建目标。容器配置存在本身不等于可复现部署已通过。

### P2：选择一项可验证的创新

- **跨来源知识关联。** [方案] 将播客段落与文献放入同一词表/模型版本，做候选召回与相关性排序，展示“该段播客对应哪些论文或问答”。与关键词检索比较 Recall@K/NDCG，并保留原文定位。这比新增聊天入口更直接体现数据融合与挖掘价值。
- **可解释学习增益。** [方案] 展示推荐分数各项贡献及原文证据，并移除主题、未知词比例、已读惩罚分别做消融实验；用人工标签说明哪些设计有效，哪些权重仍需调整。
- **分析可视化。** [方案] 增加数据质量漏斗、主题分布、用户已知/新增知识对照以及规模—耗时曲线。跨批次主题趋势须先解决模型对齐，不能直接比较不同模型的 cluster 0。
- **真实分布式对照。** [方案] 有资源时部署多个实际 executor 节点，保持数据、参数和资源预算可比较，记录 executor 分布、shuffle、耗时及瓶颈。小数据下 Spark 启动成本较高也应如实报告。[课程要求] 真实集群是加分方向，课程 PDF 并未将永久公网部署列为全部项目的前置条件。

## 建议执行顺序

[方案] 先完成“万条有效数据 + 人工评价 + 六项交付物”，再完成“评分查询优化 + 模型版本一致性 + 可复现实验”，最后选择一个跨源关联/可解释推荐创新并补充分布式对照。当前最适合的定位是**可追溯的多源技术知识分析与个性化发现系统**，以现有主线的证据和分析质量作为答辩重点。
