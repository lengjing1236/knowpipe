[已确认] 打开、收藏、通知已读不等于文档已读；读过不等于掌握。取消的用户手工标注任务不恢复。

## 3. 分布式Spark为什么用，以及对最终效果的影响

[已验证] Spark本地模式也执行真实的分区、任务与计算。Standalone集群由driver协调远端executors；它们必须能访问数据、依赖并连接driver。[官方集群说明](https://spark.apache.org/docs/latest/cluster-overview.html)

| 维度 | 当前单机Spark | 增加真实跨主机执行器后的可能变化 |
| --- | --- | --- |
| 同一资料、同一算法的推荐准确性 | 由数据、目标处理、特征和排序决定 | 不应自动提高；数值归约可能有微小误差，排序需稳定次序和容差验证 |
| 全库索引、主题与关联更新 | 受一台机器CPU、内存、磁盘限制 | 可分担任务、扩大总容量；数据足够大且分区合理时可能更快 |
| 用户等待 | 等待任务、计算、模型与翻译 | 只能缩短其中可并行的Spark阶段；下载、ASR、翻译和队列单worker瓶颈不会自动消失 |
| 可覆盖的数据 | 现在1万篇、约22万有效段落可运行 | 可为更多领域、更多全文与更频繁更新提供资源，间接增加找到好资料的机会 |
| 故障与运维 | 一台主机故障会中断服务 | executor任务可以重算；driver、Mongo、共享存储的高可用要另外设计，不能宣称加worker就全系统容灾 |
| 成本 | 配置简单，无网络shuffle成本 | 多机网络、序列化、调度、存储与运维有成本；1万篇规模完全可能比单机更慢 |
| 课程证据 | 真实计算成立，但不满足“真实分布式优于单机”的更强证据 | 提供真实多主机执行器、DAG、数据量与单机对照，不能预估具体得分 |

[方案判断] 为当前1万篇功能可运行，并非必须立即增加主机。为了后续规模/时效和课程分布式证据，需要具备可部署能力并实测。是否更快、快多少不能预先承诺。Spark官方也指出CPU、网络与内存都可能成为瓶颈，需先测量。[调优依据](https://spark.apache.org/docs/latest/tuning.html)

[必须改动] 不能只把 `local[1]` 换成 `spark://...`：
1. 保留提交时的master/driver/执行器设置，不让程序默认值覆盖；Python Standalone采用client部署模式。[提交文档](https://spark.apache.org/docs/latest/submitting-applications.html)
2. 当前JSONL、Parquet、manifest都是本机路径。第一条部署路线使用各节点相同绝对路径的共享挂载，实际验证读写和指纹；日后需要更大规模时再做HDFS/对象存储适配。
3. 分发同版本Python代码，安装相同依赖；模型留在独立服务/driver，避免每个Spark进程重复加载ASR/翻译模型。
4. 保持全库向量在分区中，保留候选/历史有界收集；验证数据倾斜、分区和driver内存。
5. 采集executors实际任务、主机/进程、输入指纹、资源和运行时间，分别标记“同机多进程测试”和“跨主机验收”。

## 4. 分阶段执行步骤与必要性

### 阶段A：当前立即执行——中文入口、对象约束与部署准备
[已实现：SpecKit Feature010阶段A工程机制；质量不足见第6节]
1. 用实际本地中→英模型解释中文学习目标，保留原目标，按原文和译文分别召回后合并；转换失败明确降级。
   - 必须改：当前有限词表无法覆盖任意计算机术语；简单拼接两种语言会稀释覆盖率，需独立计算每种目标。
2. 提取用户明确指定的技术产品/代码名及别名，候选必须有对象依据；展示对象约束和查找解释。
   - 必须改：泛词“事务”不能代替用户指定的“PostgreSQL”；这类错误靠增加机器无法修复。
3. 给目标处理器与译文处理器设置版本身份，缓存/任务绑定版本；译文加数字与代码检查及风险说明。
   - 必须改：换模型后不能继续静默展示旧模型译文；完整输出与内容正确是两个验收维度。
4. 提供外置Spark配置、共享路径/依赖预检查、同机独立执行器的固定输入对照。
   - 必须改：消除伪“只改master就支持集群”的假设；当前只验收现有硬件能证明的内容。
5. 用至少8组、4个方向的双语开发场景与真实资料运行，保留完整结果；目标变更、缓存、用户隔离及RSS回归。
   - 必须改：不再只用一个Pandas或一个PostgreSQL场景代表整个系统。

### 阶段B：中文内容达到可依赖的质量
[后续必须完成，依赖A的版本和质量记录]
1. 冻结新的真实计算机资料样本：数据库、操作系统、网络、编程；正文、代码、数字、否定/条件句分别检查。
2. 对比现有小模型与可在本机运行的更强中英目标转换、英中正文翻译及ASR；测内存、时间、漏译、术语和数值语义。010实际仍将“事务”译为service，故两个翻译方向都须改进。付费服务只有取得提供方/预算授权后才能使用。
3. 按段保存译文对应的原文范围，翻译标题和推荐解释；失败可重试、原文可查看。
4. 选择确有改善的方案后默认启用；自动完整性检查通过仍不能叫“语义正确”。教学质量未过关则本阶段保持未完成。

### 阶段C：多主题资料、分析视图与资料治理
[后续必须完成，依赖A统一输入与版本接口；覆盖审计可与B并行]
1. 统计来源×领域×语言×更新时间×全文质量，找出实际缺口；补库有主题依据，不为凑条数抓取。
2. 对照语义召回与当前词汇方法，解决操作系统调度等泛目标错配；把章节标题与相邻正文组成证据单元，不让短标题高分代替实质讲解。在当前全文库计算主题分组和跨来源相似/补充候选，保存批次、关系类型、原文证据；限制全库两两比较。
3. 新工作台展示来源分布、主题材料、关系下钻，能回到原文；不能复用旧摘要主题图冒充新分析。
4. 管理端支持更新/撤回资料，联动失效译文、特征、推荐和通知，保留审计。
5. 论文全文、公式/图表/PDF解析按真实学习主题和许可条件补充；并不要求每次推荐强行包含arXiv。

### 阶段D：验证“真正有用”并形成课程交付
[后续必须完成，可与B/C部分并行]
1. 保留009的英文检索基线；该32条集已被分析，不再冒充新的未见测试集。
2. 固定新的多领域目标、版本化已读材料和候选池；分别评价相关性、重复、可解释补充和中文可读性，报告标注来源及局限，不要求用户恢复旧批量标注任务。
3. 对照无历史、无技术对象约束、无跨语言、无去重等方案；不以额外词数量或模型自评直接等同学习收益。
4. 独立验证多期RSS、服务重启、限额/失败、长期并发。量化等待时间，区分Spark与模型阶段。定位009/010偶发浏览器401；重复通过尚不能证明该问题已修复。
5. 若以后有多台机器，在相同语料/算法/总资源记录下做多机对照，记录加速比或减速；当前这一项保持待资源。
6. 同步README、SDD、可复现命令、演示与真实Git记录，解释成果边界。

## 6. 本轮实现后，哪些问题仍未解决

[已验证] 原文/译文独立召回、技术对象证据、处理器版本与质量门禁已落地；模型更新不复用旧任务，旧worker不能降级新译文。Spark提交模式、共享目录及同机独立executor已实测，仍只有一台物理主机。

[已验证：边界] 8组双语开发目标在真实万条库完成16次检索，中文8/8非空、英文7/8非空；跨站请求伪造和操作系统调度仍有空结果/错配。真实译文仍有严重术语错误。计数、运行完成和规则检查通过，都不能替代“学生读得懂、推荐确实相关”。详情见[逐项结果](evidence/010-quality-cluster-readiness/query-review.md)。

[必须继续] 下一优先项是B的双向技术翻译质量与C的主题覆盖/语义召回；同时完成双语段落、主题关系图与资料治理，再用D验证真实用途。增加主机不会解决这些语义和内容问题。
