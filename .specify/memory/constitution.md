# 基于 Spark 与 MongoDB 的多源技术内容知识挖掘与个性化发现 Web 系统 Constitution

## Core Principles

### I. Spark 核心计算边界（NON-NEGOTIABLE）
核心挖掘计算——TF-IDF、KMeans 主题聚类、相似度计算、推荐分数——必须来自 Spark 可复现程序，
并留有可检查的运行证据（日志、DAG、条数、耗时）。LLM 只能用于推荐理由润色、阅读提示、
"可能冲突"候选生成等辅助环节；LLM 输出禁止作为核心挖掘成果替代 Spark 计算。
**理由**：这是课程对"大数据处理真实参与计算"的硬性评分依据，一旦核心结果可以由 LLM
生成，课程证据链条即失效。

### II. 知识单元级分类与可追溯性
个性化分类（known/refine/new/possible_conflict）的对象是从文档中抽取出的知识单元
（关键词或主题簇），不是整篇文档；同一篇文档允许被拆解为多个知识单元并分别判定。
每一次分类结果必须能追溯到具体判定依据：命中或未命中的关键词集合、命中的主题簇 id、
以及推荐分数的各项构成。`possible_conflict` 类别仅在有可追溯断言和判定证据时展示，
并必须经人工复核后才可对用户可见。
**理由**：文档级打标签会掩盖"同一篇文档里既有已知内容又有新内容"的真实情况，
且不可追溯的分类结果无法在答辩或人工复核中被验证。

### III. 技术选型不可替代边界
批处理场景使用 Spark，不使用 Flink/Kafka 等流处理框架，因为 Stack Exchange 与 arXiv
数据是有界历史数据，不是持续到达的流数据。存储使用 MongoDB 文档模型，不使用图/键值/
时序模型冒充，因为业务数据是字段可变的半结构化文档，不是图关系、简单键值或时序测量。
以下等价替代明确禁止：Python 线程池不能算 Spark；JSONL/SQLite 不能算 MongoDB；
CLI/Markdown 输出不能算 Web。
**理由**：技术选型必须对应数据形态和课程技术栈要求，用更易实现的方案偷换课程要求的
技术组件，会使答辩证据失去意义。

### IV. 数据规模基线
项目最终基线为不少于 10,000 条有效 Stack Exchange 文档及 arXiv 补充数据。第一技术切片
必须先用两个来源各 100 条文档打通"采集 → Spark → MongoDB → API → 页面"全链路，
验证字段、存储和接口全部贯通后，才允许扩展到万条级规模。
**理由**：先在小规模上验证全链路可行性，可以在真正投入大规模处理前发现结构性问题，
避免在数据量增大后才发现管道设计缺陷。

### V. 可评价性
核心分类与推荐结果必须能够用可复现指标评价，至少包括 Precision@K、NDCG 或人工相关性
评分之一。评价前必须设置非个性化基线（热门度排序或纯相似度排序）作为对比对象，
个性化机制的效果通过与该基线的指标差异体现，而非仅展示结果本身。
**理由**：没有基线对比的推荐结果无法证明"个性化"确实带来了改进，容易把工程实现
误当作效果证明。

### VI. 文档状态标记约定
项目文档写作沿用以下状态标记，区分规划与既成事实：`[课程要求]`（来自课程 PDF 的约束或
评分原则）、`[已验证]`（仓库材料、环境检查或公开数据调研已有证据）、`[方案]`（建议采用、
尚待实现的设计）、`[待确认]`（必须由教师或项目成员进一步确认）。新增或修改任何规划类
文档时必须使用这套标记，不得把方案写成已完成的事实。
**理由**：课程项目周期短、多人协作，未标记状态的文档容易让团队成员或教师误判项目
真实进度。

## Governance

本宪法优先于项目内其他实践文档（包括调研方案、PPT、README）。当其他文档与本宪法
冲突时，以本宪法为准，并应更新冲突文档。

**修订流程**：任何团队成员均可提出修订；修订需说明触发原因（课程要求变化、技术方案
调整、教师反馈等），并同步评估对现有 spec/plan/tasks 的影响后方可合并。

**版本策略**：采用语义化版本。移除或颠覆性重定义现有原则记为 MAJOR；新增原则或
实质性扩展现有指导记为 MINOR；措辞澄清、错字修正等非语义变更记为 PATCH。

**合规审查**：每次 `/speckit-plan` 或 `/speckit-implement` 前需对照本宪法逐条自查，
任何偏离必须在对应 spec 或 plan 文档中显式记录理由；无法证明必要性的复杂度增加应被拒绝。
